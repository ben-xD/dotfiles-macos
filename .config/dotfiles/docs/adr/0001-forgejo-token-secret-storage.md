# 1. FORGEJO_TOKEN storage for the tlduck Forgejo npm registry

- Status: Accepted. Interim implementation (macOS Keychain) in place; target
  implementation (age + age-plugin-se) pending.
- Date: 2026-07-18
- Deciders: Ben

## Context and problem statement

`@tlduck`-scoped npm packages are published to a private Forgejo registry at
`git.net.tlduck.com`. Installing them requires an auth token that npm/pnpm read
from `.npmrc`:

```ini
@tlduck:registry=https://git.net.tlduck.com/api/packages/tlduck/npm/
//git.net.tlduck.com/api/packages/tlduck/npm/:_authToken=${FORGEJO_TOKEN}
```

The `.npmrc` references the token via `${FORGEJO_TOKEN}` rather than embedding it,
so the file itself carries no secret and is safe to commit. The open question is
where the *value* of `FORGEJO_TOKEN` lives and how it reaches the shell.

Environment facts that shaped the decision:

- Single-user macOS machine on Apple Silicon, so the Secure Enclave is available.
- Shell config is generated by home-manager. `~/.zshrc` is a read-only symlink into
  the world-readable `/nix/store`, and `home.nix` is committed to this repo. A secret
  placed in `home.nix` would therefore be both committed to git and world-readable in
  the store. Disqualifying.
- An existing GPG key (`gpg@tlduck.com`) already lives on a hardware token
  (smartcard), with `pinentry-mac` configured.

## Decision drivers

- Never store the token in plaintext in a committed or world-readable file.
- Encrypted at rest, ideally gated by an interactive presence check (Touch ID or hardware).
- Free and open source.
- Low friction: opening a terminal must not prompt, but pnpm must still find the token when needed.
- Small blast radius. On a single-user Mac the real trust boundary is the user account,
  not the process, so also keep the token scoped and revocable rather than relying on
  storage alone.

## Considered options

1. **Hardcode in `.npmrc` or `home.nix`.** Rejected: plaintext, committed to git, and
   (via the nix store) world-readable.
2. **Gitignored `~/.config/secrets.env` (chmod 600), sourced at shell start.** Plaintext
   at rest. Acceptable but unencrypted.
3. **macOS Keychain via the `security` CLI.** Encrypted at rest, login-gated, never on
   disk in plaintext, never in git. But the login keychain is unlocked for the whole
   session and `/usr/bin/security` is a universal reader, so any process running as the
   user can read the token silently with no prompt. No per-process isolation, no
   biometric gate.
4. **KeePassXC.** Rejected for this use: Touch ID / Quick Unlock is a GUI-only feature.
   The `keepassxc-cli` path we would actually use has no biometrics and prompts for the
   master password on every shell. Too painful for a token pnpm needs constantly.
5. **1Password CLI.** `op` does provide Touch ID at the terminal, but it is paid and
   closed source. Ruled out on the open-source requirement.
6. **`pass` / `gopass` on the existing GPG hardware token.** Viable and reuses existing
   infrastructure; the smartcard is a hardware-possession gate (plus card PIN, and
   optional physical touch). Kept as the strong runner-up.
7. **`age` + `age-plugin-se`.** The private key is sealed in the Secure Enclave and
   decryption is gated by Touch ID. Free, open source, minimal, and independent of the
   GPG/YubiKey setup.

## Decision outcome

Chosen target: **`age` + `age-plugin-se`**.

- Generate a Secure-Enclave-backed age identity with an `any-biometry-or-passcode`
  access control (Touch ID, with Mac-passcode fallback so a failed sensor cannot lock
  us out).
- Encrypt the token to that identity's recipient and store the ciphertext at
  `~/.config/age/forgejo-token.age`. It is safe at rest because it is only decryptable on
  this Mac, gated by Touch ID. The identity file lives at `~/.config/age/forgejo-se.txt`
  (mode 600) and is kept out of git.
- Load it on demand, never at shell start, via a `forgejo-token` shell function in
  `home.nix` that decrypts into `FORGEJO_TOKEN` for the current shell.
- Remove the "remember to run it" burden with a `pnpm` shell wrapper that auto-loads the
  token on the first pnpm invocation in a project whose `.npmrc` references it: one Touch
  ID per shell, only where needed.

Interim: **macOS Keychain** (option 3) remains the active implementation in `home.nix`
until the age setup is completed. It is functional today and strictly better than any
plaintext option.

Runner-up: **`pass` on the existing GPG hardware token** (option 6). If Touch ID proves
unreliable or the Secure-Enclave binding becomes inconvenient, fall back to this rather
than to plaintext or Keychain.

## Consequences

Good:

- Token is encrypted at rest and never in git or the nix store.
- Decryption requires Touch ID, so a background process cannot read it silently, unlike
  the Keychain.
- Fully open source, no subscription.
- `.npmrc` stays committable and portable across machines and CI.

Trade-offs and costs:

- The age identity is bound to this Mac's Secure Enclave and cannot be copied to another
  machine. If the Mac is lost the token is unrecoverable via this path; recovery is simply
  to rotate/revoke the Forgejo token and re-encrypt. This is acceptable because the token
  is cheap to reissue.
- pnpm errors (`Failed to replace env in config`) on any command that reads the `.npmrc`
  while `FORGEJO_TOKEN` is unset, so the token must be loaded before pnpm runs. The wrapper
  handles this transparently.
- One Touch ID prompt per shell that installs. This is the deliberate cost of the gate.
- A biometric gate stops silent reads but not malware that waits for the user to authorize
  and then scrapes the value. This is mitigated, not eliminated, so the Forgejo token is
  kept read-only (package scope) and revocable.
